# 插件安全加固与架构优化 — 实施计划

> 来源：《插件架构评审》（2026-08-15 会话）结论落地。
> 范围：P0/P1/P2 漏洞修复 + 框架解耦改造。分四批交付，每批独立可验证、可回滚。

---

## 批次 A：P0 漏洞（资产暴露 + 安装身份绑定）

### A1. `/plugin-assets/:id/*` 仅放行 `frontend/` 子目录 + 插件状态校验

- **问题**：路由公开（`router.go:66`），Handler 只做路径穿越防护，不限制文件类型——
  匿名可下载 `plugin.exe`（二进制本体）、`pubkey.pem`、`manifest.json`、`checksums.json`；
  卸载为软删，卸载后文件仍可访问。
- **方案**：
  1. `handler/plugin.go` Asset：清理后的相对路径必须以 `frontend/` 开头，否则 404；
  2. service 层新增 `PublicAssetDir(ctx, pluginID)`：ID 白名单 + 查实例 `state == running`
     才返回目录（与 `/api/v1/plugin-extensions` 的"running 且有前端资产"语义对齐）；
     `installed`（未启用）/`disabled`/`uninstalled` 一律不暴露。
- **涉及**：`internal/handler/plugin.go`、`internal/service/plugin_runner.go`。
- **验收**：`GET /plugin-assets/{id}/plugin.exe` → 404；停用插件后 frontend 资产 404；
  现有 `plugin_test.go` 穿越用例仍通过。
- **风险**：升级期间（deactivate→替换→activate）资产短暂 404，可接受。

### A2. 安装身份绑定 + 上传通道补能力校验

- **问题**：`installFromFile` 完全信任包内 manifest 自报 ID（`plugin_bpk.go:97`），
  可注册为任意插件 ID 静默替换既有插件（`?upgrade=1`）；本地上传通道完全绕过
  `checkCompatibility`（能力/版本/冲突校验）。
- **方案**：
  1. `installFromFile` 增加 `expectedID` 参数：市场安装/升级路径传入清单 ID，
     解包后 `manifest.ID != expectedID` → 拒绝；
  2. `Manifest` 增加可选 `capabilities` 字段（打包时写入），`InstallFromBPK`
     对其做 `unknownCapabilities` 校验（未知能力拒绝）；
  3. `UpdatePlugin` 传入 `inst.PluginID` 作为 expectedID。
- **涉及**：`internal/service/plugin_bpk.go`、`internal/plugin/bpkg/manifest.go`、
  `cmd/bp/main.go`（打包写入 capabilities）。
- **验收**：伪造 ID 的包被拒；上传声明未知能力的包被拒。

## 批次 B：P1 漏洞（供应链签名 + 身份透传）

### B1. `.bpk` Ed25519 包签名体系

- **问题**：整包无第三方签名，checksums.json 为包内自证——投毒即 RCE；
  清单 SHA-256 为可选校验且市场条目普遍未声明。
- **方案**（信任模型：市场根公钥内置主站 settings，可配多把）：
  1. `bpkg` 新增固定条目 `signature.sig`：对 `checksums.json` 字节的 Ed25519 签名（64 字节原始值）；
  2. `pack.go` 新增 `PackSigned(manifest, files, privKey)`；`unpack.go` 返回验签材料；
  3. 主站 settings 新键 `plugin_pkg_pubkeys`（PEM 列表，管理员后台配置）：
     - 已配置信任公钥 → 包**必须**含签名且任一公钥验签通过，否则拒绝安装/升级；
     - 未配置 → 无签名包放行（兼容现有 4 个官方包与本地开发），清单 SHA-256 声明则比对；
  4. `cmd/bp` 新增 `-key`（私钥 PEM 路径，打包时签名）与 `keygen` 子命令（生成密钥对）；
  5. 验签发生在解包落盘**之前**。
- **涉及**：`internal/plugin/bpkg/`、`internal/service/plugin_bpk.go`、`cmd/bp/main.go`。
- **验收**：无信任公钥时现有包正常安装；配置后无签名包被拒、篡改包验签失败被拒。
- **密钥操作（部署侧，代码完成后执行）**：`bp keygen` 生成市场根密钥 →
  公钥写入主站设置 → 官方 4 插件重新打包签名 → marketplace-repo 更新。

### B1b. 升级版本钉扎

- **问题**：`installFromRelease`/`UpdatePlugin` 永远拉 `latest` Release，
  清单 version 与实际安装版本可漂移（清单过期时装到未审计版本）。
- **方案**：`ghclient` 新增 `FetchReleaseByTag`；升级路径优先按清单 `version`
  拉取 `v{version}` tag 的 Release，拉取失败再回退 latest（保持可用性）。
- **涉及**：`internal/ghclient/client.go`、`internal/service/plugin_bpk.go`。

### B2. 插件 API 代理身份透传 + 管理端点收窄

- **问题**：`/api/v1/plugins/:id/*path` 任意登录用户可调，且 `CallAPI` 不携带
  userID/role（`handler/plugin.go:116`）——插件侧无法鉴权，普通用户可触达
  qq-music 登录导入/登出/BGM 配置等管理操作。
- **方案**：
  1. 宿主侧：`Call` handler 从鉴权中间件取 userID/role，经 gRPC metadata
     （`x-plugin-user-id` / `x-plugin-user-role`）随调用下发（不改 proto，无需重新生成 pb）；
  2. SDK 侧：`serve.go` 从流/metadata 读出身份注入 APIMux 请求 context；
     `sdk.go` 新增 `CallerID(ctx)` / `CallerRole(ctx)`；
  3. 插件侧：qq-music / netease-music 的管理端点（登录导入、登出、BGM 开关、歌单配置）
     校验 `CallerRole` 为管理员角色，`visitor` 一律 403；
  4. 公开音乐播放代理（`/music/qq-url` 等）保持匿名——只读播放地址，风险可接受。
- **涉及**：`internal/handler/plugin.go`、`internal/service/plugin_runner.go`、
  `internal/plugin/proxy.go`、`pkg/plugin-sdk/`、`cmd/qq-music-plugin/`、`cmd/netease-music-plugin/`。
- **验收**：visitor 调用 `/api/v1/plugins/qq-music/logout` → 403；管理员正常。

## 批次 C：P2 漏洞

### C1. capability 门控改为「实例登记 ∩ 二进制自报」

- **问题**：`manager.go:187` 用插件进程 `Info()` **自报**能力决定 data.read 授权——
  恶意二进制自报即得手。
- **方案**：
  1. 迁移 `016_plugin_capabilities.sql`：`plugin_instances` 加 `capabilities` JSONB 列；
  2. 安装/升级/重装时把市场清单（或包内 manifest）声明的 capabilities 落库；
  3. `PluginManager` 新增 `capabilityProvider` 回调（延迟绑定，同 licenseProvider 模式），
     Start 时 `allowed = intersect(登记能力, 自报能力)`，data.read 门控用 allowed。
- **涉及**：`db/migrations/`、`internal/repository/plugin.go`、`internal/service/plugin*.go`、
  `internal/plugin/manager.go`、`internal/server/server.go`（装配）。
- **验收**：登记无 `data.read` 的插件即使自报也拿不到 brokerID。

### C2. GitHub OAuth 加 state 防 CSRF

- **方案**：`AuthorizeURL` 生成 128bit 随机 state，内存 TTL 表（10 分钟）存储；
  `Callback` 校验 state 匹配后销毁。单实例部署够用（多实例需换 Redis，留注释）。
- **涉及**：`internal/service/oauth.go`。

### C3. 后台 settings 接口敏感键过滤

- **问题**：`admin.go:413` `Settings()` 全量回显 settings 表，含
  `gh_oauth_token`、`plugin_license_private_key`（AES-GCM 密文）等——扩大离线爆破面。
- **方案**：定义敏感键名单（密文/凭证类），返回时以固定掩码 `"__SECRET__"` 替代；
  `SaveSettings` 收到掩码原值的键**跳过不覆盖**（防回填破坏）。
- **涉及**：`internal/service/admin.go`。

### C4. zip 解压实际长度校验

- **问题**：`unpack.go:43` 只查 zip 头声明的 `UncompressedSize64`，谎报可绕过单文件上限；
  超限条目被静默截断。
- **方案**：`io.ReadAll(LimitReader(rc, Max+1))` 后检查 `len(content) > MaxFileBytes` → 拒绝。
- **涉及**：`internal/plugin/bpkg/unpack.go`（一行 + 单测）。

## 批次 D：框架解耦改造

### D1. Handshake 常量下沉独立包

- **问题**：宿主 `manager.go:23` 导入插件侧 `pkg/plugin-sdk/server` 仅取 Handshake 常量，
  依赖方向错误，`serve.go:19` 注释自认"修改需两侧同步"。
- **方案**：新建 `pkg/plugin-sdk/handshake` 小包持有 `HandshakeConfig`；
  两侧引用同一份；`server` 包保留 `Handshake` 别量兼容既有插件源码。
- **涉及**：新包、`internal/plugin/manager.go`、`pkg/plugin-sdk/server/serve.go`。

### D2. hook.go 平行表合并

- **问题**：`syncHooks`/`knownHooks`/`allHookNames` 三张平行表，新增钩子需手工同步 4 处（僵化）。
- **方案**：单张 `map[string]HookSpec{Name, Sync}` 作为唯一事实源，
  其余集合/函数由包级推导生成，导出接口签名不变。
- **涉及**：`internal/plugin/hook.go`。

### D3. 钩子 Priority 生效

- **问题**：`sdk.Hook.Priority` 声明后从未使用（死字段），调度按注册顺序执行。
- **方案**：调度器分发时按 Priority 升序排序（小先执行）；进程外适配器统一默认优先级
  （proto HookInfo 无 priority 字段，改 proto 需重生成 pb，本轮不做——SDK 侧字段注释同步修正）。
- **涉及**：`internal/plugin/dispatcher.go`、`pkg/plugin-sdk/sdk.go`（注释）。

### D4. music.go 插件 ID 收敛为注册表

- **问题**：`handler/music.go` 四处写死 `"netease-music"`/`"qq-music"` 插件 ID（脆弱性）。
- **方案**：收敛为包级 `musicProviders` 映射（provider 名 → 插件 ID）+ 未运行时友好报错。
  完全可插拔（插件声明 `music.provider` 能力 + 标准解析契约）列为后续批次 E，
  因前端 URL/解析器同样按源定制，需整体设计。
- **涉及**：`internal/handler/music.go`。

### D5.（后续批次 E，本轮不做，仅记录）

- iframe 沙箱接线（`sandbox.ts` 已实现未使用）；
- 插件前端共享 SDK 抽取（escapeHtml/试播逻辑三处复制）；
- `Start` 握手阶段移出全局锁；
- manager 日志注入 zap（替换 fmt.Fprintf(os.Stderr)）；
- 资产版本化缓存（`?v=` + 协商缓存）；
- AIKeySecret 不再回退 JWT_SECRET（涉及存量密文迁移，需单独设计）。

> （见验收报告「批次 E」）。以下 E1/E7 经用户确认追加实施：

### E1. iframe 沙箱接线（追加实施）

- **目标**：为第三方插件提供强隔离前端形态——`sandbox.ts`（iframe + postMessage +
  1 小时短期 token）从死代码转为可用通道。
- **方案**：
  1. 插件前端 manifest 的 `pages[].sandbox: true` 声明走 iframe 沙箱（缺省仍走同源 ESM）；
  2. plugin-pages 壳按声明分发：sandbox 页面 mountSandbox（iframe），否则现有 ESM 模式；
  3. 共享 SDK 增加 `createSandboxApi()`（postMessage 客户端封装，iframe 页面侧使用）；
  4. 开发手册补沙箱页面接入章节。
- **涉及**：`frontend/src/plugins/sandbox.ts`、`internal/pluginshared/shared.js`、
  plugin-pages 壳、`docs/plugin-development.md`。

### E7. 音乐源完全可插拔（追加实施）

- **目标**：新增音乐源插件不改宿主代码（`music.provider` 能力 + 标准解析契约）。
- **方案**：
  1. 市场清单新增 `music_provider` 字段（provider 名，如 "qq"/"netease"）；
  2. 宿主桥接通用化：`GET /api/v1/music/:provider/url?src=`（公开）、
     `GET /api/v1/music/:provider/bgm`（公开）——按清单声明 + running 状态动态发现
     provider→插件 ID 映射；旧端点（qq-url/netease-url/qq-bgm）保留兼容，内部走通用逻辑；
  3. 插件标准契约端点：`POST /music/url`（body {src}，源特定标识 → 播放地址）、
     `GET /music/bgm`（背景音乐配置 + 歌曲列表聚合，可选实现）；
  4. qq-music / netease-music 实现标准端点（BGM 聚合逻辑从宿主 QqBGM 移入 qq 插件）；
  5. 前端嵌入解析器（music-embed.ts）按源定制属产品形态，保持现状。
- **涉及**：`internal/service/plugin_market.go`、`internal/handler/music.go`、
  `internal/router/router.go`、`cmd/qq-music-plugin/`、`cmd/netease-music-plugin/`、
  `marketplace-repo/`、`docs/plugin-development.md`。

## 验证与交付

- 每批次后：`go build ./...` + `go test ./...` 全量通过；
- 完成后：按市场根密钥流程重打包官方 4 插件验证签名链路；
- 输出 `discuss/插件安全加固与架构优化-验收报告.md`。

## 明确不做（YAGNI）

- 不引入容器/seccomp 等操作系统级沙箱（Windows 部署为主，收益/成本比不成立，
  信任模型改为"签名链 + 管理员审核"）；
- 不改 proto 重新生成 pb（身份走 metadata，避免全插件强制升级 SDK）；
- 不做 TUF 完整元数据协议（单根公钥 + 轮换即可满足当前规模）。
