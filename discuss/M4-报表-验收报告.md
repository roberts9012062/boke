## 一、数据报表页（/admin/reports，设计稿《数据报表》）

- **页头**：「数据报表」+「近 30 日趋势 · 导出 CSV」+ 近 7 日/近 30 日切换 + 导出 CSV 按钮 + 刷新按钮
- **4 统计卡**：浏览/获赞/评论（近 7 日 + 环比，口径与仪表盘一致）+ 今日新帖（**N 待审需处理**徽标 = 评论待审数，与待处理块联动）
- **四维趋势柱状图**：浏览/新帖/获赞/评论（`ReportTrendSeries`：post_views 按日计数 + generate_series 补零；7/30 日可切换，30 日柱宽自适应）——补足了仪表盘趋势无浏览维度的缺口
- **内容分布环形图**（复用 donut-chart）+ **最近动态**（复用仪表盘样式）
- **待处理块**（设计稿：评论待审 N（处理）/ 内容举报 N（查看）/ 敏感词命中 N（复核），带跳转链接）
- **CSV 导出**：`GET /admin/reports/export.csv?days=`（附件流，UTF-8 BOM 便于 Excel，5 列 × N 行）

## 二、备份导出（/admin/backup，设计稿《备份导出》）

- **表单**（`backup-form.tsx` 对齐画板）：备份类型（全站数据/媒体库 单选卡）、范围（内容+用户+媒体 复选，媒体库隐藏）、保留天数（默认 30，1-365）、导出格式（JSON/CSV/ZIP，媒体库锁定 ZIP + 提示）、立即备份（成功/失败反馈）
- **备份记录列表**：类型/状态（成功/失败徽标）/文件/大小/时间/操作（下载/删除二次确认）
- **应用级导出**（用户确认方案，标准库零依赖）：
  - 全站数据 JSON：范围表 → 单 JSON 文件（posts/comments/tags/post_tags/users/media_assets）
  - 全站数据 CSV：每表独立 CSV（键序稳定 + BOM）→ 打包 ZIP
  - 全站数据 ZIP：data.json + manifest.json（应用/时间/范围）
  - 媒体库：data/media 目录递归打包 ZIP（空目录生成空 zip）
  - 通用行导出（`SELECT *` 动态列名），不绑定实体结构
- **过期清理**：创建备份后同步删除同类型早于保留天数的旧备份（文件 + 记录；实测 3 天前记录随保留 1 天新备份被清）
- **安全**：下载/删除前 `safePath` 校验（file_path 必须以 backup 目录为前缀，防越权）；失败备份落 failed 记录

## 四、过程问题

1. **CountWhere 复用失败**：报表「今日新帖」误用 PostRepo.CountWhere（需完整 WHERE + 参数占位，无参场景参数不匹配）→ 改为 AdminRepo.CountTodayPosts 专用方法
2. **categories 表不存在**：设计稿范围文案含「分类」，但库中实际为 tags + post_tags → 导出表清单修正（差异记录）
3. **CSV 备份文件名**：多表 CSV 打包 zip 但扩展名 .csv → 修正为 .zip
4. **report.go 变量与函数重名**：局部变量 trend 与 trend() 函数冲突 → 改名 trendSeries
5. **backup.go 431 行超规范**：文件打包辅助（zipDir/zipFiles/marshalCSV 等）拆至 backup_files.go（327+113 行）
6. GUI 首次加载等待不足（Next dev 首编译慢）→ 等待元素出现后断言全过
